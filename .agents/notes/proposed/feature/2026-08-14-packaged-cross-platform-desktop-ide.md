# Agent Note: Packaged cross-platform desktop IDE

Status: proposed

English | [中文](2026-08-14-packaged-cross-platform-desktop-ide.zh.md)

## Problem

DeepSeek Harness ships interactive Web and headless applications, but it does not ship an installable desktop IDE. The Web application requires a live Host process and currently sends workspace-file actions to the operating system instead of opening files inside the application. A static renderer bundle cannot provide agent execution, filesystem access, session persistence, settings, or credentials by itself.

The first desktop release must run on macOS and Windows without a system Node.js or pnpm installation and without asking the user to keep a terminal or local HTTP server open. It must reliably edit existing text, source-code, and Markdown files; switch Markdown between source and preview; save with the platform shortcut; prevent silent overwrites when an agent and a user edit the same file; and open files produced by an agent in the internal editor.

This work spans a desktop carrier, a workspace-scoped file capability, a Client plugin, profile composition, native runtime packaging, signing, and installed-artifact tests. Treating it as a static Web build or a single UI component would leave the privileged Host behavior and distribution lifecycle undefined.

## Proposal

Add a packaged Electron application that reuses the existing Web Client and Host plugin graph while replacing the Web server and browser transport with a local asset protocol and a narrow IPC carrier. Electron owns the window and application lifecycle. A bundled plain Node.js 24 sidecar owns Cordis, the agent runtime, filesystem services, subprocesses, persistence, settings, and credentials. Electron Forge packages and signs separate artifacts for each supported operating system and architecture.

The packaged application opens no listening port and does not require a separately managed server. Source development may continue to use the existing Web carrier through an `ide` profile, but installed artifacts use only the desktop carrier.

### First-release product contract

| Capability | Required behavior |
| --- | --- |
| Text and code | Browse registered workspaces, open existing regular UTF-8 files in tabs, edit buffers, and preserve unsaved tab state while switching files. |
| Markdown | Edit `.md` and `.markdown` source and switch the active tab between source and a preview rendered from the current unsaved buffer. |
| Save | Handle `Meta+S` on macOS and `Control+S` on Windows, acknowledge durable Host writes before clearing dirty state, and keep the buffer dirty after failure. |
| Concurrent edits | Serialize the user's save with Agent edits made through Harness file tools, save against the version returned by read, retain the user's buffer after a stale-version failure, show the current disk content and a diff, and never overwrite silently within that Host-mediated path. |
| Agent-produced files | Route existing tool locations, deliverable chips, and inline file mentions to the desktop editor, reuse an open tab, and reveal the file in the IDE surface. |

The first release edits existing files only. Creation, deletion, rename, move, copy, filesystem watching, global search, Git UI, an interactive terminal, full language-server completion and diagnostics, WYSIWYG Markdown, PDF or DOCX editing, remote Web IDE access, third-party desktop Client plugins, user-defined desktop Agent presets, and in-app preset switching are outside this scope.

Add a shipped source-development template named `ide` with `[@deepseek-ai/dsh-base, @deepseek-ai/dsh-web-app, @deepseek-ai/dsh-ide-app]`, and add the IDE bundle to the CLI dependency closure. This makes `dsh --profile ide` a valid browser-based development entry point rather than relying on an implicit custom profile.

The desktop executable directly boots `[@deepseek-ai/dsh-base, @deepseek-ai/dsh-web-app, @deepseek-ai/dsh-ide-app, @deepseek-ai/dsh-desktop-app]`. The carrier refactor leaves row `connection` mapped to `@deepseek-ai/dsh-client-connection` and row `modules` mapped to `@deepseek-ai/dsh-client-modules`; these stable core rows continue to own Client graph injection, `ctx.connection.rpc`, `ClientModuleSystem`, and the `__DSH_MODULES__` bootstrap exception. The Web bundle selects `@deepseek-ai/dsh-client-connection-web` on row `connection-transport` and `@deepseek-ai/dsh-client-modules-web` on row `module-delivery`. The Web transport sends envelope-bearing POST requests through the logical router and delegates ApiProxy GET and HEAD routes without an RPC envelope to the existing physical Fetch handler. The desktop patch disables the real `web-startup`, `webserver`, `web-runtime`, and `client-hmr` rows; `frontend-static` is a child of `web-runtime`, not an independent row. It replaces only `connection-transport` and `module-delivery` with their desktop providers, replaces row `directory-picker` with `@deepseek-ai/dsh-host-directory-picker-electron`, replaces base row `subprocess` with `@deepseek-ai/dsh-subprocess-guardian`, and inserts workspace registration, desktop directory-flow, `agent-presets-desktop` admission and roster, and IDE rows. ApiProxy unary calls, Typert interceptors, and the `events.mux` and `events.host` downlink streams therefore retain the same dispatch graph. Startup requires one core and exactly one provider for each carrier capability, exactly one desktop preset-admission contribution, and no user preset root.

The desktop transport has an explicit Host-side method allowlist. It rejects legacy renderer-supplied `workspace.create({ path })`, direct `host.pickDirectory`, `host.openPath({ path })`, and `agentPreset.select`. It narrows `session.create` to `{ workspaceId, sessionId?, agentPreset? }`: `workspaceId` is required, `cwd` is forbidden, `agentPreset` is omitted or exactly `desktop-default`, and omitting both authority fields never falls back to the Host default directory. The desktop conversation flow requires an active registered workspace and sends its `WorkspaceId`; the underlying Host method resolves that identifier through the authoritative registry and applies the desktop preset admission before it can create a directory or start an Agent. The desktop directory-flow contribution calls `workspaceRegistration.pickAndRegister()`; the Host BFF invokes `ctx.directoryPicker`, canonicalizes and registers the selected root, and returns only the resulting workspace view. The Remote has no fixed unary deadline because the dialog is user-paced. Caller cancellation or renderer destruction aborts the BFF and makes Electron main discard any later chooser result; it does not promise to close the native chooser programmatically because Electron's [`showOpenDialog`](https://www.electronjs.org/docs/latest/api/dialog) exposes no abort handle.

Extend the existing directory-flow owner with an `onRegistered(workspace)` result. The desktop contribution uses that result directly; the Web native and browse contributions retain their current `onPicked(path)` flow and Client-side create call. Exactly one contribution occupies each directory-flow slot.

`apps/desktop` packages and injects its own shipped preset root through app-boot configuration and sets the omitted-preset default to `desktop-default`; it does not depend on the CLI launcher's `SHIPPED_PRESET_ROOT`. The first roster contains only `desktop-default`, which inherits the root Host `ctx.fs` and guardian-backed `ctx.subprocess`, mounts ordinary filesystem and shell tool consumers, and contains neither a PTY consumer nor a nested filesystem or subprocess provider. The CLI `minimal` preset and user preset roots are not exposed because they can mount persistent-terminal behavior or isolated filesystem and subprocess providers.

Add a preset-admission extension point to `agent-presets` and invoke it before every resolve, mount, recompose, `standingKeyFor`, cold transcript ensure, create, resume, and fork path; a composed generation carries proof that admission already ran, so `composeFrom` cannot accept an unvalidated generation. The desktop contribution admits only `desktop-default`, and the desktop UI hides switching. Raw `agentPreset.select` is rejected atomically without changing the current preset. A recorded unsupported preset returns stable `desktop-preset-unsupported` metadata without first mounting any provider or starting an Agent. Such sessions remain usable through Web/headless carriers.

`desktop-default` inherits the exact root filesystem service instance used by `workspaceFiles`, so Agent file-tool saves and editor saves share one per-target lock and version authority. Its filesystem tool consumers and policies cannot replace desktop-owned providers. This immutable first-release roster makes PTY absence, guardian ownership, and the cross-surface conflict guarantee properties of every desktop Agent graph rather than best-effort validation of arbitrary user composition.

The IDE registers a root-scoped surface through `shell.overlay` and an action in the existing `sidebar.footer.action` slot. This surface is available before a session exists, unlike `conversation.view`, and it can retain tabs while the user returns to the existing conversation UI. Replacing the root shell is unnecessary.

### Desktop runtime and IPC

The desktop application uses the following lifecycle:

1. On Windows, Electron handles every `--squirrel-*` lifecycle event, including install, update, uninstall, and obsolete, before acquiring the single-instance lock or starting the sidecar, performs only the requested lifecycle work, and exits.
2. Electron acquires the single-instance lock, resolves the signed resource directory and user-data directory, and starts a bundled runtime guardian. The guardian starts the plain Node.js sidecar with an explicit desktop composition and private IPC channels.
3. The sidecar boots Cordis and returns the same `BootManifest` used by the Web Client, with immutable `dsh-app://plugins/<id>/client.js?rev=<revision>` bundle URLs, plus readiness or startup failure over child IPC. It never listens on TCP.
4. Electron registers a read-only `dsh-app://` protocol for signed renderer assets and the manifest-whitelisted first-party Client bundles. A fixed signed desktop bootloader first awaits `invoke('desktop.bootManifest')`, validates the shared manifest, assigns `window.__DSH_BOOT__` in the renderer main world, and only then dynamically imports the existing shell. The existing `ClientModuleSystem.loadBundle()` loads plugin URLs as classic scripts, and each bundle must complete the existing module-factory registration check.
5. A sandboxed preload exposes only versioned `invoke` and `subscribe` methods. Each invocation and subscription has an identifier, disposal message, and abort path; renderer destruction, timeout, or transport loss aborts the corresponding Host `AbortSignal` and rejects pending calls. Renderer-to-main bodies use transferred Electron MessagePorts. Electron main translates them to versioned JSON child IPC so the bundled Node guardian never consumes Electron's V8-specific structured-clone format. Binary body chunks use exact-key canonical-base64 envelopes with declared and configured byte limits; the guardian restores their semantic bytes, then proxies them to the same-Node sidecar over advanced serialization. The sequenced protocol carries acknowledgement, end, and cancel frames. A `DesktopApiClient` implements the existing abstract fetch transport through `invoke`; the desktop provider dispatches requests into `ctx.connection.rpc` and carries both Host event streams through `subscribe`.
6. Application quit first asks Cordis to dispose and waits for bounded graceful shutdown. If the sidecar hangs or crashes, the guardian kills and joins its registered process tree before Electron exits. No child, worker, subprocess, or persistent terminal may survive the last window.

Use `contextIsolation: true`, `nodeIntegration: false`, renderer sandboxing, `webSecurity: true`, a restrictive Content Security Policy, denied arbitrary navigation and window creation, sender validation on every IPC handler, and typed wire validation at the preload and sidecar boundaries. The renderer never receives Node.js, Electron, absolute-resource-path, credential, or generic process-execution APIs. This follows Electron's current [security guidance](https://www.electronjs.org/docs/latest/tutorial/security) while preserving the repository's deferred zero-port Electron direction.

The Host runs under the bundled plain Node.js executable rather than the Electron main process. This keeps `process.execPath`, Node engine behavior, native-addon ABI selection, process inspection, and child cleanup consistent with the existing Host assumptions. The pinned Node.js build must satisfy the repository engine floor.

The guardian protocol is the only generic process-creation authority in the desktop composition. The subprocess capability changes ordinary `spawn()` to return `Promise<SubprocessHandle>`, and every local, E2B, fixture, invariant, and tool consumer migrates to the asynchronous result. The `subprocess-guardian` sidecar provider sends a spawn specification to the guardian. On Windows, each spawn gets its own kill-on-close Job Object: the guardian creates the process suspended, assigns it to that handle-specific Job, completes stdio and ownership registration, and only then resumes it. Handle termination affects only that Job, `waitForExit()` waits for its active-process count to reach zero, and guardian failure closes every retained Job handle to terminate all managed trees. On macOS, Electron main first starts and records a fixed signed process-capsule helper as a unique process-group leader before it may receive a target specification; the helper accepts no renderer calls or executable path from main. The guardian gives the target specification to that capsule, which creates the stopped child inside the already mirrored process group. The capsule reports the child PID and confirms the PGID to both guardian and Electron main, waits for both ownership acknowledgements, and only then resumes the target. The guardian returns a spawn acknowledgement containing the real PID, after which the provider resolves the handle; it never fabricates PID `-1` or a not-yet-owned handle.

The guardian provider preserves every `SubprocessSpawnSpec` stdio disposition. Pipe mode exposes Node `Readable` and `Writable` proxies. Inherit mode relays diagnostics to the matching sidecar descriptor. Collect mode feeds exact stdout or stderr bytes into `subprocess-collector`; the capsule does not resume the target until the sidecar has installed the requested pipe or collector and acknowledged stream readiness. The collector's bounded tail and independent synchronous `readFrom(fullStreamByteOffset)` reader are the provider-neutral core shared by local, guardian, and E2B providers. Local and guardian providers also use its Host-readable drain and finalization lifecycle.

Host-local providers may enable collector-owned spill files with private permissions, whole-stream caps, clean-close publication, and post-exit readability. E2B instantiates the collector in memory-only mode and remains the sole owner of remote spill creation, cap enforcement, validity, and path publication. Memory-only collection creates no Host temporary directory; the default private spill directory is resolved and created only when an actual Host spill begins. Local and guardian withhold an incomplete Host spill after transport or final-close failure, while E2B independently withholds an incomplete remote spill.

`subprocess-guardian.resolveExecutable()` runs in the guardian execution world and preserves the existing capability rules: reject empty names; verify, canonicalize, and require executability for absolute paths; resolve bare names against the scrubbed guardian PATH plus explicit environment overrides; reject relative names containing separators; report not found distinctly; and propagate cancellation. Spawn revalidates the returned executable before capsule resume, applies the existing scrubbed child environment plus explicit overrides and tombstones, and never inherits Electron-only entries. The provider does not fall back to Electron's environment or resolve on the renderer.

Stdin, stdout, and stderr use the same sequenced child-IPC framing with process and file-descriptor identifiers, bounded chunks, acknowledgements, and the hop-wide credit pool. Exhausted credit pauses guardian pipe reads, each stdin write completes only after acknowledgement, and end, error, signal, wait, collector finalization, and cancellation states propagate exactly once. On macOS, every capsule monitors guardian and main liveness pipes: guardian loss makes the capsule kill and join its group, while capsule loss makes Electron main use its read-only ownership mirror to kill and join the recorded PGID. The supervisor forwards a real target exit before any synthetic outcome: an empty PGID does not prove the capsule event pipe is drained, so it drains a queued `EXIT` before publishing `GROUP_ZERO`. Requested termination synthesizes a missing outcome only after the capsule is reaped and its event source reaches EOF; event-source exhaustion without a requested termination or target outcome is a native error followed by group cleanup, not a fabricated target result. This second owner covers guardian failure after resume and the capsule remains responsible during sidecar hangs or crashes. A load-time invariant requires the guardian provider on the desktop `subprocess` row and rejects any direct local spawn provider in the desktop composition.

The desktop module-delivery provider is the only replacement for Web `/plugins/*` delivery; there is no preload module-execution path. The first release packages a closed, signed set of first-party Client plugins. The sidecar supplies identifiers, revisions, injections, and load timing in the shared manifest, while Electron maps each allowed URL to an immutable packaged asset. User-installed Host-only plugins remain possible when their deployment does not require renderer code; third-party desktop Client plugin loading requires a separate trust and signing design.

The Electron directory-picker provider implements the existing Host capability rather than exposing a renderer shortcut. Workspace UI calls `workspaceRegistration.pickAndRegister()`; that Host operation invokes the capability, the sidecar provider sends a typed Host-initiated request over child IPC, and Electron main opens the native dialog. A selected path returns only to the still-live Host operation. Cancellation marks the request terminal and discards a late result without registering a workspace; parent-window destruction follows platform chooser behavior rather than a nonexistent close API.

### Workspace file service

Implement `WorkspaceFilesGateway` as a Typert business Remote backed by the workspace registry and `ctx.fs`. Normal file operations identify a branded `WorkspaceId` and an array of relative path segments. Only `resolveLocation` accepts an absolute-or-relative candidate because existing model-facing `FileLocation.path` values can be absolute.

| Operation | Result |
| --- | --- |
| `workspaceFiles.list({ workspaceId, directory })` | Return the canonical relative directory and stable entries with `name`, `segments`, `kind`, and optional `size`. Out-of-workspace links appear as blocked and are not traversed. |
| `workspaceFiles.read({ workspaceId, path })` | Return `content` and an opaque `WorkspaceFileVersion` for an existing regular UTF-8 file. |
| `workspaceFiles.save({ workspaceId, path, content, expectedVersion })` | Under the Host provider's target lock, replace the file only when `expectedVersion` still matches, returning a new version or an explicit `version-conflict` result. |
| `workspaceFiles.resolveLocation({ workspaceId, location })` | Resolve a `{ path, line? }` candidate relative to the workspace root when needed, enforce canonical containment in the Host, and return canonical path segments, file kind, text support, and the optional line. |

`WorkspaceFileVersion` is a branded wire string that the Host maps to and from `FsVersion` without parsing. The service exposes no blind replace or force-write operation. An explicit conflict-resolution action first reads the latest version and then performs another compare-and-swap save; a second intervening change produces another conflict.

The reliable conflict guarantee covers editor saves and Agent mutations performed through Harness filesystem tools in an accepted desktop preset, because both inherit the same root provider instance and share its per-target lock and version check. Direct writes by shell commands or external applications are non-cooperating cross-process mutations: ordinary version checks detect changes outside the narrow probe-to-replace race, but the existing filesystem seam does not promise cross-process linearizable compare-and-swap. The UI must not describe that residual case as guaranteed.

Every operation resolves `WorkspaceId` through the authoritative registry, resolves the canonical workspace root and target again, and proves containment with `ctx.fs.contains()`. Segment-based operations reject empty segments, `.`, `..`, NUL, embedded separators, Windows drive paths, and UNC paths. `resolveLocation` treats its candidate as untrusted, resolves a relative candidate against `workspace.path`, and rejects alternate-casing aliases or symlink and junction targets that escape the canonical root. Save repeats canonical resolution and containment immediately before the atomic write.

Read captures a file version before bounded streaming, captures it again after decoding, and returns content only when the versions match. A concurrent mutation yields `changed-during-read`, never old content paired with a new version. Save delegates to `ctx.fs.writeText()` with `replaceIfVersion` and the explicit per-call policy `{ mode: 'workspace-write', workspaceRoot: workspace.path }`; it does not call `node:fs` directly or inherit a deployment fallback root.

Extend the filesystem Service Definition with required `listDirBounded(path, { maxEntries })`. Every shipped local, E2B, sandbox, invariant, fixture, and test provider must stop at `maxEntries + 1` and return `too-large` without delegating to unbounded `listDir()`; directories within the limit are sorted before return. No default implementation may materialize the complete directory.

Config owns `maxTextFileBytes`, `maxDirectoryEntries`, `maxDesktopBodyBytes`, `maxDesktopChunkBytes`, and `maxDesktopInflightBytes`; proposed defaults are 10 MiB, 10,000 entries, 160 MiB, 1 MiB, and 16 MiB. The desktop connection UTF-8 encodes request, response, and downlink-event bodies. Renderer-to-main transfers use request- or subscription-scoped Electron MessagePort streams with bounded `Uint8Array` chunks. Main-to-guardian transfers use versioned JSON control frames and bounded canonical-base64 binary envelopes; guardian-to-sidecar transfers use advanced serialization only between the identical bundled Node runtimes. Both child-IPC hops retain the sequenced and acknowledged protocol and a bounded in-flight window. `invoke` and `subscribe` carry only control metadata and stream handles. Each physical hop counts the aggregate body, applies backpressure, propagates cancellation and disconnect, and rejects the body above `maxDesktopBodyBytes`. A hop-wide credit pool shared by all concurrent bodies caps queued and unacknowledged bytes at `maxDesktopInflightBytes`, rather than multiplying the per-stream window by the number of calls. Startup fails unless the total body limit covers the existing prompt/attachment body contract and the worst-case JSON escaping of `maxTextFileBytes`, and unless the chunk and in-flight limits form a nonzero credit window; tests include the current 100 MiB aggregate-image request and a 10 MiB all-escaping text buffer. The Host independently aborts an oversized file read before full Host allocation and rejects an oversized save before filesystem write. These limits do not prevent the editor from allocating its current buffer.

Stable business failures are `workspace-not-found`, `invalid-path`, `outside-workspace`, `not-found`, `not-directory`, `not-regular-file`, `not-text`, `too-large`, `permission-denied`, `changed-during-read`, and `version-conflict`. Transport and lifecycle failures remain infrastructure errors.

Canonical re-resolution prevents static escapes and swaps completed before the final containment fence. The existing filesystem threat model still accepts the residual race in which a trusted local process replaces an ancestor between that final check and the operating-system syscall; this proposal does not claim descriptor-relative or handle-relative containment.

### Editor behavior

Use CodeMirror 6 for the first release and load language support on demand. The tab identity is `(workspaceId, pathSegments)`. Each tab retains `baseContent`, `baseVersion`, current buffer content, a monotonically increasing local revision, dirty state, and save state. Switching tabs or opening the conversation surface must not discard this state.

Markdown source and preview are two views of the same in-memory buffer. Preview reuses the existing `MarkdownText` pipeline for GFM, math, and syntax highlighting. Raw HTML, `file:` links, and arbitrary local paths remain inert. Workspace-relative image loading is deferred until it has a bounded, workspace-aware asset resolver.

The save command snapshots content, base version, and local revision at invocation. The tab clears dirty state only after the Host acknowledges the write and the current local revision still equals the submitted revision. If the user types during the save, the acknowledged content and returned version become the new base, but the newer buffer remains dirty. IPC, policy, disk, or shutdown failures preserve the buffer and expose a retry action.

On `version-conflict`, the editor keeps the local buffer, reads the latest disk content, and shows local-versus-disk differences with three explicit actions: continue editing, reload from disk, or overwrite the displayed latest version. Reload requires confirmation when local changes exist. Overwrite performs a new compare-and-swap against the displayed disk version and can conflict again; there is no unconditional write path.

Agent mutation events that identify an open file may refresh a clean tab or present the conflict state immediately for a dirty tab. Versioned save remains the final authority for races, changes from external applications, and mutations that were not observed as events. Filesystem watching is not required for the first release.

Closing a dirty tab, changing workspace with dirty tabs, or quitting the application requires an explicit save, discard, or cancel decision. A crash may lose unsaved buffers in the first release; durable draft recovery is a later feature and must not be implied by session persistence.

### Agent-produced file handoff

Add an effect-scoped asynchronous Client file-opener arbiter with `tryOpen({ sessionId, location }): Promise<'handled' | 'unhandled'>`. Change the owning conversation action from `openFile(path: string): void` to an awaited `openFile(location: FileLocation): Promise<void>`, and make tool rows, produced-file locations, deliverable chips, and inline mentions preserve the complete `{ path, line? }` value. After every internal handler returns `unhandled`, the owner invokes a carrier-scoped fallback: Web uses the existing operating-system opener, while desktop reports an unsupported or outside location without calling the arbitrary-path API.

The desktop handler maps the session to a registered workspace and calls `workspaceFiles.resolveLocation`; only the Host converts an absolute or relative model-facing path into canonical segments. A handled text location opens or reuses the matching tab, reveals the IDE overlay, and positions the optional line after read. Unsupported files, directories, outside paths, and unregistered locations show an inert diagnostic in the desktop profile instead of reaching any operating-system opener. This prevents a compromised renderer from turning workspace scripts, executables, shortcuts, or application bundles into a process-execution primitive.

The Web profile keeps its current operating-system opening behavior. Internal editing is a desktop/IDE profile contribution, not a global change to workspace links or the conversation UI.

### Packaging and release matrix

Use Electron Forge with pinned Electron, Forge, maker, Node.js, and native dependency versions. Forge's `package` and `make` stages are extended with deterministic Host-deploy assembly and artifact verification; Forge does not replace the repository's TypeScript, Web, Cordis, or release-family builds.

| Target | Required artifacts | Release gate |
| --- | --- | --- |
| macOS arm64 | `.dmg` plus `.zip` containing the Developer ID-signed, notarized, and stapled `.app` | Native Apple Silicon runner; hardened runtime; nested signature verification; DMG notarization and stapling; cold launch on a clean account. |
| macOS x64 | `.dmg` plus `.zip` containing the Developer ID-signed, notarized, and stapled `.app` | Native Intel runner; the same signature, notarization, and cold-launch checks; no unverified universal merge. |
| Windows x64 | Authenticode-signed and timestamped Squirrel `Setup.exe` plus portable `.zip` from the signed application directory | Native Windows runner; Setup, installed-directory, and ZIP-content signature verification; install, launch, upgrade, uninstall, and portable-start checks. |
| Windows arm64 | Deferred | No support claim until native dependencies, signing, and the complete packaged smoke pass on native hardware. |

Electron Forge normally packages the current platform and architecture and recommends native CI for cross-platform releases. The release workflow therefore builds macOS artifacts on macOS and Windows artifacts on Windows instead of treating a cross-compiled directory as a releasable product. The `.dmg`, Squirrel installer, and ZIP makers are configured explicitly; MSI is deferred until there is an enterprise deployment requirement. Squirrel's `*-full.nupkg` and `RELEASES` outputs are verified build intermediates but are not published until automatic updates enter scope.

The packaged resource tree contains Electron, a pinned plain Node.js 24 runtime, the built Host deployment, the desktop-safe preset roster, signed renderer assets, first-party Client bundles, worker files, language and font chunks, licenses, and every target-specific native module or executable in the resolved dependency graph. Electron main and preload have no native-addon dependencies. The plain-Node sidecar closure is installed separately for Node.js 24 and the target operating system and architecture, excluded from Forge's Electron-ABI rebuild, and copied into resources after any Electron rebuild but before final signing. The Host deployment remains outside ASAR when Node module resolution, dynamic loading, workers, or executable permissions require real files.

Remove `spawnTerminal()` from `SubprocessRuntime` and move it to the independent `SubprocessPtyRuntime` service. Terminal consumers inject `ctx.subprocessPty`, and the Web/local composition mounts `subprocess-pty-local`, whose only native runtime dependency is `node-pty`. The desktop profile omits that provider and disables persistent-terminal consumers, so its resolved deploy graph contains neither `node-pty` nor the macOS spawn helper; accidentally enabling a PTY consumer fails loud at load on its missing required service. Normal agent shell commands remain available through the guardian-backed macOS bash and Windows PowerShell providers. Windows packaging verifies the Koffi-backed guardian Job Object, ACL, and atomic JSONL paths but disables the Koffi directory picker in favor of the Electron provider. Every platform uses the bundled Node.js executable to load every sidecar `.node` payload and separately probes Sharp, ripgrep, worker-thread, and other resolved native or executable payloads. Landlock payloads are not included in macOS or Windows artifacts.

`apps/desktop` remains a non-private member of the existing `dsh` npm release family and follows its version, pack, verification, publication, and tag sequence. Forge installers and archives are additional non-npm assets attached to that same release tag. Mutable state never resides inside the application directory. Windows Squirrel install, upgrade, and uninstall and macOS copy, replacement, and removal of the `.app` must preserve `DSH_HOME`, registered workspaces, sessions, settings, and credentials. Automatic update delivery is deferred, but replacing an older signed application with a newer one is a release-blocking smoke test.

### Security and data safety

The packaged renderer is unprivileged. All workspace access, agent operations, and process work cross typed request and event IPC methods with configured aggregate-body and chunk limits and validated senders. Directory dialogs use a typed sidecar-to-main capability request. The application loads only packaged local content, denies unexpected protocols and navigation, and never evaluates a workspace document as renderer code.

Workspace and session authority is rooted in a `WorkspaceId` issued by Host-owned registration, not a renderer-supplied absolute path or default cwd. Canonical containment, symlink and junction checks, regular-file checks, size limits, UTF-8 decoding, sandbox policy, and versioned writes are enforced by the Host on every request. The desktop method allowlist blocks raw root registration, cwd-based or authority-free session creation, and arbitrary external opening; renderer checks improve diagnostics but do not grant authority.

The Markdown preview preserves the current sanitizer and URL policy. Conflict recovery preserves both the user's buffer and the latest disk text until the user chooses an action. No autosave, reload, Agent event, installer operation, or shutdown path may silently discard a dirty buffer or overwrite a newer file version.

Signing credentials remain CI secrets. Packaged-artifact verification enumerates and validates nested executables, native modules, helpers, and application resources before publishing. Third-party notices cover Electron/Chromium and bundled executable payloads in addition to npm packages.

### Testing strategy

| Layer | Required coverage |
| --- | --- |
| Host package | Unit tests for bounded list across every provider, read, save, `resolveLocation`, size and text limits, version mapping, exactly-one-winner Host-mediated saves, explicit workspace-write policy, forged-root rejection, stable errors, and containment rejection on POSIX and Windows path forms. |
| Desktop transport | Tests for MessagePort and child-IPC chunk ordering, hop-wide in-flight credit under concurrent streams, aggregate limits, 100 MiB attachment flow, worst-case text escaping, mid-stream cancellation, peer disconnect, and guardian forwarding in both directions. |
| Desktop preset policy | Tests run admission before resolve, mount, recompose, `standingKeyFor`, cold transcript ensure, create, resume, and fork; reject raw `agentPreset.select` without changing the current preset; admit `desktop-default`; and prove an unsupported recorded preset mounts no filesystem, subprocess, or PTY provider. |
| Subprocess capability | Contract tests migrate every provider and consumer to async `spawn()`, require a real acknowledged PID, cover empty, absolute, bare, missing, and non-executable lookup cases, PATH overrides, invalid relative names, lookup cancellation, and child-environment tombstones, then cover all three stdio dispositions, independent collected offsets, tail rollover and `lossy`, spill success and cap failure, post-exit reads, drain-before-settlement, exhausted-credit pause and resume, signal, wait, cancellation, two concurrent Windows Jobs with one-handle termination isolation, guardian and capsule crashes, exactly-once stream and collector termination, Windows close-all-Jobs cleanup, and macOS mirrored-PGID cleanup. |
| Client package | Component tests for tabs, dirty state, unsaved Markdown preview, platform shortcuts, save-in-flight editing, retry, conflict diff and actions, dirty-close prompts, and file-opener routing. |
| Assembled application | A keyless journey that registers a temporary workspace, creates a `desktop-default` session by `WorkspaceId`, edits text/code/Markdown, previews unsaved Markdown, saves, creates a real Agent-produced-file location, clicks it into the editor, and exercises a concurrent Agent-file-tool conflict through the shared root filesystem provider. |
| Packaged application | Native-runner smoke with no system Node.js or pnpm, a temporary `DSH_HOME`, offline start, the assembled journey, a real bash or PowerShell command using collected stdout and a bounded spill, clean and forced shutdown, restart persistence, Windows install/upgrade/uninstall, and macOS app copy/replace/remove preservation. |
| Artifact integrity | Target-specific probes for every native module under bundled Node.js, helper, executable, worker, Client bundle, nested asset, signature, notarization ticket, Squirrel output, and installer path shipped by the resolved deploy graph. |

Path-security tests reject absolute paths on segment-only operations, parent traversal, sibling roots, static symlink and junction escapes, swaps completed before the final canonical containment fence, Windows drive and UNC forms, and casing aliases. Each rejected request proves that no byte outside the registered workspace was created or modified. The accepted residual post-fence operating-system race is documented and is not represented as prevented.

Desktop-authority tests prove that the renderer cannot call raw workspace creation, direct picking, or arbitrary-path opening; forge or replay a picker result; alias a selected root; or use a valid `WorkspaceId` to access a sibling root. They reject raw `session.create({ cwd })`, `session.create({})`, missing or forged `WorkspaceId`, the combined `cwd` plus `workspaceId` form, every preset other than `desktop-default`, and raw `agentPreset.select`, then prove that no outside directory was created, no provider mounted, and no Agent started. The native picker selection is consumed inside the user-paced Host BFF call; cancelling that call before a chooser result prevents later registration, and unsupported executable or script locations never reach an OS opener.

The concurrency test reads one version into two writers, releases both saves together, and requires exactly one success and one `version-conflict`. The losing editor retains its local buffer, displays the winning disk content, and cannot dismiss the state through an implicit overwrite.

Packaged smokes run on macOS arm64, macOS x64, and Windows x64. They start from the actual DMG/ZIP or installer output, open a workspace, complete all first-release user flows, quit the last window, assert that the sidecar and descendants are gone, restart offline, and confirm that workspace registration, settings, sessions, and user files remain intact. Windows additionally exercises every `--squirrel-*` event before sidecar startup and proves that lifecycle-only invocations never boot the Host.

Failure-path smokes inject a crash after process creation but before resume and acknowledgement, leave a real subprocess group running, then separately hang and crash the sidecar, crash the guardian with that live group, crash the macOS capsule after ownership mirroring, destroy the renderer with pending calls and subscriptions, and force application replacement. Windows must prove Job kill-on-close; macOS must prove capsule liveness cleanup and Electron-main mirrored-PGID cleanup. Every stopped child and running group must be killed and joined, while IPC peers receive cancellation or disconnect failures rather than hanging.

The Client UI remains a plugin and slot contribution under [GUI Web Client architecture](../../implemented/architecture/2026-07-19-gui-web-client-architecture.md).

Workspace operations are a new GUI consumer of the existing [filesystem capability seam](../../implemented/architecture/2026-06-17-filesystem-capability-seam.md) and its opaque versions, not a parallel Electron filesystem implementation. The residual canonicalization and replacement races remain the ones documented by the [cross-family filesystem sandbox](../../implemented/feature/2026-07-14-cross-family-fs-sandbox.md) and [filesystem absence observation](../../implemented/bug-fix/2026-08-09-filesystem-absence-observation.md). ## Alternatives considered

**Ship a standalone static frontend.** Rejected because the renderer cannot execute agents, enforce filesystem policy, persist sessions, or provide credentials without a live Host runtime.

**Run the Host inside Electron main.** Rejected because Electron's Node ABI and `process.execPath` semantics differ from the Host's plain-Node assumptions, and a Host failure would share the window-management process. A bundled plain Node.js sidecar provides a clearer lifecycle and native dependency target.

**Start the existing loopback Web server from Electron.** Rejected for the packaged product because privileged file operations would remain on an HTTP/WebSocket surface, port and token lifecycle would become product behavior, and the repository already reserves IPC for Electron. The browser-based `ide` development profile still uses the Web carrier.

**Use Tauri as the first carrier.** Viable, but it still requires a Node sidecar for the existing Host and adds a Rust command bridge and packaging system. Electron directly reuses the Client runtime and matches the existing architecture direction.

**Use Monaco in the first release.** Rejected because its workers and language assets increase package and startup cost while the first release needs reliable text editing rather than a VS Code runtime. CodeMirror 6 supplies the required editor behavior; Monaco remains an option if later requirements justify it.

**Keep operating-system file opening only.** Rejected because it cannot provide shared dirty state, Markdown preview, save conflict handling, or a direct Agent-to-editor flow. It remains the behavior of the Web profile; the first desktop release leaves unsupported locations inert.

**Produce one SEA executable.** Rejected for the first release because dynamic plugin resolution, renderer assets, workers, native modules, helpers, Electron, and the current lack of a Windows Web-runtime pipeline make the application directory a clearer verifiable unit. Platform packages may contain multiple signed executables.

## Acceptance criteria

1. Native release jobs produce and verify macOS arm64 and x64 DMG/ZIP artifacts containing signed, notarized, and stapled applications, plus timestamped Windows x64 Squirrel Setup and portable ZIP artifacts whose executable contents are signed.
2. Every installed artifact launches offline on a clean machine without system Node.js or pnpm and without opening a listening TCP port or terminal window.
3. A user can browse a registered workspace and open, edit, tab-switch, and save existing UTF-8 text, source-code, and Markdown files.
4. Markdown preview renders the current unsaved buffer, source/preview round trips without modifying source text, and raw HTML and local-file URLs remain inert.
5. `Meta+S` on macOS and `Control+S` on Windows clear dirty state only after a durable acknowledged write; failure and in-flight edits preserve dirty content.
6. Under the immutable `desktop-default` preset, a Host-mediated Agent file-tool write and an editor save from the same base version use the same root filesystem provider and yield exactly one success and one visible conflict; no IDE or Harness file-tool path performs an unconditional overwrite, and the losing buffer remains recoverable. Cross-process shell and external writes retain the explicitly documented residual race.
7. Clicking a real Agent-produced-file location, including an absolute model-facing path, is resolved by the Host and opens or reuses the correct internal editor tab at its optional line without also opening externally; unsupported locations remain inert.
8. Host tests prove that malformed segment paths, escaping candidates, symlinks, junctions, and swaps completed before the final containment fence cannot read or modify bytes outside the registered workspace; desktop session creation cannot use a raw, omitted, or forged cwd authority; and the accepted residual post-fence race remains explicit.
9. Closing dirty state requires save, discard, or cancel, and clean quit, a fault before guardian spawn acknowledgement, sidecar hang, sidecar crash, guardian crash with a live group, macOS capsule crash, renderer destruction, and forced replacement leave no owned sidecar, stopped child, worker, subprocess, or persistent terminal alive and no pending IPC call without cancellation.
10. Windows Squirrel install, upgrade, uninstall, and lifecycle-only invocations and macOS app copy, replacement, and removal preserve `DSH_HOME`, registered workspaces, sessions, settings, credentials, and workspace files, and the complete native packaged smoke passes on every supported target.

## Risks

- IPC boot, Client plugin loading, and Web boot could diverge. Keep one boot-manifest contract, keep core graph rows carrier-neutral, and run shared built-client journeys against both carriers.
- Native modules, helpers, and signing order can produce packages that build but fail after installation. Assemble on native runners and execute payload probes from the final artifact before signing verification and publication.
- Large directories, files, prompts, and attachments can exhaust renderer or IPC memory. Require bounded enumeration in every provider, bounded reads, streamed fixed-size IPC chunks, aggregate body limits compatible with all existing calls, hop-wide in-flight credit budgets, and startup capacity assertions while acknowledging the editor's in-memory buffer allocation.
- Conflict UX can still cause data loss through a misleading action. Preserve both versions, require explicit destructive confirmation, and keep every overwrite compare-and-swap protected.
- Windows path aliases, junctions, ACL limits, and external process behavior differ from POSIX. Treat native Windows tests as release authority rather than Wine or cross-build results.
- Host-mediated version checks are not a cross-process filesystem transaction. Keep the supported Agent-edit guarantee on Harness file tools, label shell and external races accurately, and revisit OS-specific hardening in a separate filesystem proposal.
- Making ordinary subprocess creation asynchronous touches every provider and consumer. Land that capability migration with cross-provider contract tests before adding the guardian provider; never preserve the old signature through placeholder handles.
- Preset selection can bypass provider ownership through recompose or cold composition. Keep the first desktop roster immutable, run Host admission at every preset composition entry point, and add user presets only through a later design that preserves the same invariants.
- Electron expands the security and patch surface. Pin supported versions, follow upstream security releases, enforce fuses and renderer isolation, and make runtime upgrades part of normal maintenance.
- Disabling the interactive terminal narrows the first desktop product relative to the Web bundle. State the limitation in release notes and keep ordinary shell tools available to agents.
- Editor, Git, search, LSP, terminal, and update requests can expand the first release beyond its reliability target. Gate additions behind separate notes after the five required workflows ship.
